# ADR 0001: UUIDv7 IDs plus readable names
Status: Accepted. Date: 2026-10-24. Plan ref: phased plan sec 3.1.

## Context
IDs are a mix today: `Uuid::new_v4()` session tokens, `Uuid::nil()` placeholders (`crates/bosc-runtime/src/auth_guard.rs` `header_uuid`, `resolve_session`), and hard-coded `comp_default`. The owner decided that IDs are UUIDs plus readable names.

## Decision
```sql
id    uuid NOT NULL PRIMARY KEY,   -- UUIDv7 (RFC 9562), generated by the kernel
code  text NOT NULL,               -- readable name, e.g. 'SALES', 'acme-mfg'
UNIQUE (tenant_id, code)           -- per tenant (add company_id for company-scoped objects)
```
- The kernel generates IDs with `uuid::Uuid::now_v7()` (crate feature `v7`). Clients never supply primary keys on insert, and the API ignores or rejects them.
- `00000000-0000-0000-0000-000000000000` (nil) is **never valid** as an id of a user, tenant, company or record. Code that would produce it must return an error instead.
- Readable `code`: `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. Display names are separate (`name`).
- Text form: lowercase hyphenated. JSON: string.

## Consequences
- The IDs sort by time, so B-tree indexes stay compact. Leaking creation time to an attacker is acceptable.
- APIs and URLs can use `code` for people and `id` for machines.

## Alternatives considered
UUIDv4 (random, poorer index locality), bigint sequences (not merge-safe across tenants or nodes), ULID (not a UUID type in Postgres).

## Reversibility
COSTLY once data exists, because changing the type of the key column is a migration. Changing the generator version is cheap.

## Phase / enforcement
P0: new tables and generators use v7. P1: a nil user/tenant id gives 401/400 (D2 addendum d), enforced in staging/production.
